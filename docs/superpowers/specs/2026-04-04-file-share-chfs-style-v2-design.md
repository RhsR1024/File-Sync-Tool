## 1. 设计目标

本次目标不是“照抄 CHFS”，而是在当前项目已有的 Tauri + Vue 3 + Rust/Axum 架构上，把现有文件共享 v1 升级为一套更接近 CHFS 使用体验的 v2：

1. 桌面端提供完整的共享配置、权限控制、持久化和启动策略配置。
2. Web 端从“只读浏览页”升级为“可权限控制的文件管理页”。
3. 配置在软件重启、电脑重启后仍然存在，并能按设置自动重新开启共享。
4. 仍然保持当前工具“局域网、轻部署、零客户端安装”的产品定位。

## 2. Superpower 分析结论

这不是一个“补几个按钮”的小改动，而是一个跨 5 个子系统的扩展任务：

1. 桌面端配置界面升级
2. 文件共享运行时模型与持久化模型升级
3. 认证、会话、权限、IP 过滤安全层升级
4. Web 文件管理界面与读写操作升级
5. 启动链路与自动重启恢复升级

因此不建议把它作为一个单次大 PR 直接硬做，而应该拆成分阶段实现：

1. 先补齐持久化、权限模型、会话模型和安全能力
2. 再补读写 API 与删除/重命名/搜索等核心操作
3. 最后切换到新的 Web 管理界面，并补自动启动与联调验收

## 3. 当前已实现能力快照

截至 2026-04-04，当前文件共享工具已经具备这些能力：

1. 桌面端可添加多个共享目录。
2. 可配置端口。
3. 可选全局密码保护。
4. 可启动/停止 HTTP 文件共享。
5. 可展示主访问地址、备用 LAN 地址、二维码。
6. Web 端可浏览根目录与子目录。
7. Web 端可下载单文件。
8. Web 端可打包下载目录 ZIP。
9. Web 端有简单登录页。
10. Web 端支持中英文切换。
11. 桌面端可看到连接 IP 列表和运行日志。

当前实现的关键限制也非常明确：

1. 认证只有“单个全局密码”，没有账户体系，也没有读写权限矩阵。
2. Web 端没有上传、新建、重命名、删除、搜索、图片预览。
3. 没有黑白名单。
4. 没有会话时长配置，Cookie 也不是严格意义上的会话模型。
5. 没有配置持久化；页面刷新或应用重启后不会自动恢复目录、端口、密码策略。
6. 没有“软件启动时自动开启共享”或“系统启动后自动开启共享”的完整链路。
7. 当前 `connection_count` 更接近“历史访问过的唯一 IP 数”，不是真正的活跃会话数。

## 5. 方案选型

### 方案 A：继续只用 Rust 字符串模板扩展现有 Web 页面

优点：

1. 与当前 `fileshare.rs` 现状最接近。
2. 不需要额外 Web 构建产物。

缺点：

1. 上传、搜索、预览、重命名、删除、权限感知渲染都会让 Rust 内嵌 HTML/JS 快速失控。
2. 可维护性差，后续每加一个交互都会让 `fileshare.rs` 继续膨胀。

### 方案 B：保留 Rust/Axum 服务端，新增一套轻量 Web SPA 管理端

优点：

1. 最适合承载 CHFS 风格的复杂文件管理交互。
2. 可以复用项目现有 Vue 3 / TypeScript 技术栈。
3. 桌面页和 Web 页可以共享类型定义与交互语义。

缺点：

1. 需要增加 Web 静态资源的构建与嵌入流程。
2. 初始改造量高于方案 A。

### 方案 C：继续服务端渲染，但用更多原生 JS 做渐进增强

优点：

1. 变更量介于 A 和 B 之间。
2. 不需要完整 SPA 管道。

缺点：

1. 最终容易落到“既没有 Rust 模板简单，也没有 SPA 清晰”的中间地带。
2. 权限、上传进度、搜索结果态管理仍然会比较难维护。

### 推荐方案

推荐 **方案 B**。

原因很直接：你要的能力已经从“文件浏览器”升级成“Web 文件管理器”。这类交互如果继续堆在 Rust 字符串模板里，短期看省事，长期会明显拖慢后续维护和二次迭代。v2 应该把“文件共享运行时”与“Web 管理界面”边界拆开：

1. Rust 负责状态、认证、权限、文件系统操作和 HTTP API。
2. Vue Web UI 负责工具栏、列表、弹窗、上传、搜索和预览。

## 6. v2 总体架构

### 6.1 逻辑分层

1. **桌面端配置层**：`FileSharePage.vue` 负责共享配置、权限配置、持久化开关和状态展示。
2. **运行时服务层**：Rust `fileshare` 模块负责共享生命周期、认证、权限校验、IP 过滤、文件操作和事件推送。
3. **Web 管理层**：独立 Web UI 通过 HTTP API 与服务层交互。
4. **持久化层**：保存文件共享配置、权限模型、启动策略，但不向前端回传明文密码。

### 6.2 推荐模块拆分

建议把当前单文件 `src-tauri/src/fileshare.rs` 拆成目录模块：

```text
src-tauri/src/fileshare/
  mod.rs
  model.rs
  persist.rs
  auth.rs
  ops.rs
  search.rs
  http.rs
  web_assets.rs
```

核心职责：

1. `model.rs`：共享配置、账户、权限、会话、状态模型
2. `persist.rs`：本地持久化、敏感字段 hash 化
3. `auth.rs`：登录、Cookie、会话 TTL、权限校验、IP 过滤
4. `ops.rs`：列目录、上传、新建、重命名、删除、下载、ZIP、预览
5. `search.rs`：当前共享根 / 整个服务器搜索
6. `http.rs`：Axum 路由、API handler、下载流
7. `web_assets.rs`：Web 管理端静态资源输出

## 7. 数据模型设计

### 7.1 持久化配置模型

```ts
type PermissionPreset = 'read_only' | 'read_write' | 'custom';
type DeleteMode = 'recycle_bin' | 'permanent';
type IpFilterMode = 'off' | 'whitelist' | 'blacklist';

interface FileShareRoot {
  id: string;
  alias: string;
  path: string;
  enabled: boolean;
}

interface FileSharePermissionSet {
  browse: boolean;
  download_file: boolean;
  download_archive: boolean;
  upload_file: boolean;
  upload_directory: boolean;
  create_directory: boolean;
  create_text: boolean;
  rename: boolean;
  delete: boolean;
  preview_image: boolean;
  search_current: boolean;
  search_global: boolean;
}

interface FileShareAccount {
  id: string;
  name: string;
  enabled: boolean;
  preset: PermissionPreset;
  permissions: FileSharePermissionSet;
  password_set: boolean;
}

interface FileShareSavedConfigView {
  port: number;
  roots: FileShareRoot[];
  guest_access_enabled: boolean;
  accounts: FileShareAccount[];
  session_ttl_minutes: number;
  ip_filter_mode: IpFilterMode;
  ip_rules: string[];
  image_preview_enabled: boolean;
  thumbnail_enabled: boolean;
  delete_mode: DeleteMode;
  remember_settings: boolean;
  auto_start_on_page_open: boolean;
  auto_start_with_windows: boolean;
}
```

### 7.2 密码与敏感信息策略

v2 不建议继续用通用 `save_kv/load_kv` 直接保存前端原始配置，原因是：

1. 账户密码不能以明文 JSON 长期落盘。
2. 自动恢复共享需要“可用的认证配置”，但不需要把明文密码再暴露回前端。

因此 v2 采用专用 Rust 持久化：

1. 前端保存时把“新密码”提交给 Rust。
2. Rust 负责 hash 后再落盘。
3. 前端加载时只看到 `password_set: true/false`，不会看到旧密码。

### 7.3 首轮默认配置策略

由于当前功能还未正式上线，不需要为历史版本承担迁移包袱，v2 直接采用新的持久化结构作为唯一配置模型。

首轮默认值建议为：

1. 首次进入文件共享页时生成空的 `roots` 列表，端口默认沿用当前 v1 的 8080。
2. 内建 `guest` 账户始终存在，默认 `guest_access_enabled = true` 且权限预设为 `read_only`。
3. `session_ttl_minutes` 默认 30。
4. `ip_filter_mode` 默认 `off`。
5. `image_preview_enabled = true`，`thumbnail_enabled = false`。
6. `delete_mode = recycle_bin`。
7. `remember_settings = true`，`auto_start_on_page_open = false`，`auto_start_with_windows = false`。

## 8. 权限与会话设计

### 8.1 权限模型

桌面端对外展示为“预设 + 自定义”两层：

1. **只读**：浏览、下载文件、下载目录 ZIP、当前页搜索、全局搜索、图片预览
2. **读写**：只读能力 + 上传文件/目录 + 新建目录/文本 + 重命名 + 删除
3. **自定义**：按按钮级别勾选

这样既保留 CHFS 风格的直观开关，也不会把桌面 UI 直接做成一个难以理解的 12 列权限矩阵。

### 8.2 账户模型

v2 采用：

1. 一个内建 `guest` 账户，负责未登录或访客登录场景
2. 多个可选命名账户，适合团队共享

这样既能满足“密码控制”，也能满足“不同账户不同权限”。

### 8.3 会话模型

当前实现只是把密码 hash 写进 Cookie，v2 需要升级为真正的服务端会话：

1. 登录成功后生成随机 session token
2. Cookie 只保存 token
3. 服务端保存 `account_id + expires_at + client_ip + last_seen_at`
4. 会话时长采用**滑动过期**，默认 30 分钟
5. 会话过期后，Web 端自动跳转登录页并提示“会话已过期”

### 8.4 IP 过滤

IP 规则支持：

1. 单 IP，例如 `192.168.0.15`
2. CIDR，例如 `192.168.0.0/24`

过滤顺序：

1. 先做 IP 过滤
2. 再做登录与权限校验

这样可以在“登录页出现之前”就拦截不应访问的来源。

## 9. 文件操作与安全设计

### 9.1 Web 端新增操作

v2 新增：

1. 上传文件
2. 上传目录
3. 新建目录
4. 新建文本
5. 重命名文件/目录
6. 删除文件/目录
7. 当前页面搜索
8. 整个服务器搜索
9. 图片预览

### 9.2 路径安全原则

所有读写操作都必须走统一安全层：

1. 先解析共享根
2. 再 canonicalize 目标路径
3. 校验目标必须仍在共享根之内
4. 禁止跨共享根 rename/move
5. 禁止通过 `..` 或符号链接逃逸

### 9.3 删除模式

提供两种删除模式：

1. `回收站删除`
2. `真实删除`

推荐默认值为 **回收站删除**。  
如果回收站删除失败，不自动降级为真实删除，而是直接报错，避免误删。

### 9.4 搜索语义

需要在 spec 中把“搜索”定义清楚，避免后续实现歧义：

1. **当前页面搜索**：只过滤当前目录列表，前端本地执行，按文件/目录名匹配
2. **整个服务器搜索**：服务端递归所有启用共享根，按名称匹配，默认最多返回 500 条

v2 不做文件内容全文搜索，只做**名称搜索**。

### 9.5 图片预览语义

v2 的“图片预览”定义为：

1. 支持常见图片格式：`png/jpg/jpeg/gif/webp/bmp`
2. 点击文件名或预览图标可打开预览弹层
3. 可选缩略图列表模式由 `thumbnail_enabled` 控制

v2 不做视频预览，也不做复杂缩略图缓存系统。

### 10.3 桌面端交互要求

1. 共享目录的 `alias` 必须可编辑，不能只自动生成。
2. 账户权限默认用“只读/读写/自定义”下拉选择，自定义时再展开细粒度选项。

4. “开机后自动打开文件共享”应在桌面端有明确提示：这依赖保存的配置可用。
5. 若配置中存在密码已设置但前端不可见，应显示“已设置，若需修改请重新输入新密码”。

## 11. Web 端界面设计

### 11.1 目标布局

```text
┌─ 顶栏 ──────────────────────────────────────────────────────────────┐
│ 面包屑 | 当前共享根 | [上传文件] [上传目录] [新建文本] [新建目录]   │
│ [搜索框.....................][当前页面/整个服务器] [登录/用户菜单]  │
└─────────────────────────────────────────────────────────────────────┘

┌─ 内容区 ────────────────────────────────────────────────────────────┐
│ 名称                         大小        修改时间        操作         │
│ 📁 folder-a                  -           2026-04-04      下载ZIP 重命名 删除 │
│ 📄 note.txt                  2 KB        2026-04-04      下载 预览 重命名 删除 │
│ 🖼 image.png                 1.2 MB      2026-04-03      预览 下载 删除       │
└─────────────────────────────────────────────────────────────────────┘

┌─ 弹层/抽屉 ──────────────────────────────────────────────────────────┐
│ 登录弹层 / 上传进度 / 新建文本编辑器 / 图片预览 / 删除确认          │
└─────────────────────────────────────────────────────────────────────┘
```

### 11.2 Web 端关键行为

1. 没有写权限时，不显示上传、新建、重命名、删除按钮。
2. 没有搜索权限时，隐藏对应搜索模式。
3. 没有图片预览权限时，图片文件只显示下载。
4. 整个服务器搜索结果需要额外展示“所属共享根 + 相对路径”。
5. 上传目录优先使用浏览器目录上传能力；不支持该能力的浏览器降级为多文件上传。

### 11.3 Web 端移动端策略

1. 顶栏操作在窄屏下折叠为“操作”菜单。
2. 搜索框独占一行。
3. 图片预览使用全屏抽屉。
4. 行操作从横向按钮组折叠为更多菜单。

## 13. 持久化与启动设计

### 13.1 配置持久化

v2 需要持久化：

1. 共享目录列表
2. 端口
3. 访客与账户权限配置
4. IP 黑白名单
5. 图片预览与删除模式
6. 会话时长
7. 自动开启策略

### 13.2 启动策略分层

建议拆成 3 个开关，避免语义混乱：

1. `remember_settings`：保存当前文件共享配置
2. `auto_start_on_page_open`：打开文件共享页时，若服务未启动则自动恢复
3. `auto_start_with_windows`：应用随系统启动后，后台自动恢复文件共享

其中第 3 项要在设置页中显式展示，因为它影响整机启动行为。

## 15. 验收标准

1. 关闭并重新打开应用后，共享目录、权限配置、IP 过滤、会话时长、删除模式仍然存在。
2. 开启“打开本页时自动开启共享”后，进入文件共享页可自动恢复共享。
3. 开启“开机后自动打开文件共享”后，系统启动并拉起应用时可自动恢复共享。
4. Web 端能根据权限显示或隐藏上传、新建、重命名、删除、搜索、预览入口。
5. 会话超过配置时长后自动失效。
6. 黑名单命中时被拒绝访问；白名单模式下非白名单 IP 无法进入登录页。
7. 删除模式为回收站时，文件进入系统回收站；删除模式为真实删除时，直接删除。
8. 当前页面搜索只过滤当前目录；整个服务器搜索能跨共享根返回结果。
9. 图片预览只对允许的格式和有权限的用户开放。
10. 现有“文件下载、目录 ZIP 下载、二维码、备用访问地址、日志面板”能力不回退。

## 16. 明确不做的内容

为防止范围继续膨胀，v2 明确不做：

1. WebDAV 协议兼容
2. 文件内容全文检索
3. 在线编辑 Office / Markdown / 图片标注
4. 每个子目录单独 ACL
5. 跨共享根移动文件
6. 视频转码或缩略图缓存系统

---

## 17. 设计结论

当前文件共享 v1 已经具备“浏览 + 下载”的基础骨架，但与你提出的 CHFS 风格目标之间，真正缺失的是三件事：

1. **安全与权限模型**
2. **可写文件管理能力**
3. **可持久恢复的桌面控制台**

因此 v2 的正确做法不是继续补零散按钮，而是以“持久化配置 + 权限会话 + Web 文件管理器”三个核心支柱重构文件共享工具。只要这三层站稳，你提到的 CHFS 关键功能点就都能自然落进去，而且后续还可以继续扩展。
