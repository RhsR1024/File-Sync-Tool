# 硬盘缓存清理 IPSAN 资源组扩展设计

**日期**: 2026-04-27  
**范围**: 在现有“硬盘缓存清理”工具中，为 IPSAN 区域补充资源组视图、资源归属展示、资源组缓存操作，并统一优化所有区域的“缓存详情入口”交互。  
**实现分支**: `main`  
**关联文档**:

- [2026-04-23-disk-cache-cleanup-local-ipsan-design.md](./2026-04-23-disk-cache-cleanup-local-ipsan-design.md)
- [2026-04-22-disk-cache-cleanup-design.md](./2026-04-22-disk-cache-cleanup-design.md)

---

## 1. 决策摘要

本次扩展采用以下设计决策：

1. `IPSAN` 仍然保留为页面一级区域，不新增新的一级“资源组”卡片。
2. `IPSAN` 区域内部升级为双子视图：
   - `单台 IPSAN`
   - `资源组`
3. 默认主视角为 `单台 IPSAN`，因为资源组建立在单台 IPSAN 基础之上；没有单台 IPSAN，就不会存在资源组。
4. `资源组` 不是纯展示关系，而是独立资源对象：
   - 有独立状态
   - 有独立缓存存在判断
   - 有独立查看详情
   - 有独立单条/批量清理动作
5. `单台 IPSAN` 视图中必须展示“所属资源组”信息，便于按单机排查时直接看到归属关系。
6. `本地盘 / IPSAN / 资源组` 的状态枚举统一走同一套状态胶囊样式和状态说明区。
7. 当前“缓存存在 + 下一行单独一个查看详情按钮”的交互过重，统一改为：
   - 在“缓存存在”旁边直接放一个轻量详情入口
   - 入口采用眼睛图标按钮或短文本按钮
   - 不再占两行，不再显示笨重的独立“查看详情”按钮块
8. 上述详情入口简化规则必须同时应用于：
   - Linux 本地盘
   - Windows 本地盘
   - 单台 IPSAN
   - 新增的 IPSAN 资源组

---

## 2. 方案对比与选型

### 方案 A：IPSAN 区域内部双子视图（采用）

结构：

- 页面仍是 `本地盘` + `IPSAN` 两个一级区域
- `IPSAN` 卡片内部新增胶囊式子视图切换：
  - `单台 IPSAN`
  - `资源组`

优点：

- 符合“优先单台 IPSAN”的使用顺序
- 不打破当前页面的一、二级层次结构
- 资源组可以拥有完整独立操作，同时不会稀释单台 IPSAN 的主视角
- 与现有本地盘 `Windows / Linux` 子切换模式一致，认知成本低

缺点：

- `IPSAN` 卡片内部状态比之前更多，需要分清“当前子视图动作”与“整个 IPSAN 区域数据刷新”

### 方案 B：一张混合层级表（未采用）

结构：

- 资源组作为父行
- 展开后显示成员 IPSAN
- 未归组 IPSAN 归到一个“未分组”虚拟组

不采用原因：

- 主视角会变成“先看组，再看设备”，与当前需求相反
- 单台运维动作会被关系结构压住
- 资源组和设备两类动作混在同一主表中，噪音更大

### 方案 C：IPSAN 上下平铺两张表（未采用）

结构：

- 上半部分单台 IPSAN
- 下半部分资源组

不采用原因：

- 归属关系需要上下对照，效率差
- 页面变长，操作区重复
- 视觉上会把资源组误读成与 IPSAN 同级的一块独立模块

## 3. 数据来源与关系推导

### 3.1 接口来源

单台 IPSAN 继续来自：

- `POST /openAPI/system/v1/IPSAN/list`

资源组来自：

- `POST /openAPI/system/v1/IPSAN/resourceGroup/list`

### 3.2 必须推导出的关系数据

基于两个接口的响应，前端最终需要拿到以下视图模型信息：

- 每台 `IPSAN -> 所属资源组`
- 每个 `资源组 -> 成员 IPSAN 列表`
- `未归组 IPSAN` 列表
- `已归组 IPSAN 数量`
- `资源组数量`

### 3.3 异常关系兜底

如果资源组接口中出现某个成员 IPSAN，但该成员不在 `IPSAN/list` 返回结果中，页面需要保留该成员记录并标记异常，例如：

- `成员数据不完整`
- `未在 IPSAN 列表中返回`

这样可以避免接口数据不一致时，归属关系被静默吞掉。

### 3.4 缓存 key 约定

本设计默认以下 key 规则成立：

- 单台 IPSAN：`Storage:{IPSANId}`
- 资源组：`Storage:{groupId}`

如果后端实际资源组缓存 key 规则不同，则仅调整数据适配和清理目标，不改变页面结构与交互。

## 4. IPSAN 区域信息架构

### 4.1 IPSAN 卡片头部

标题仍为 `IPSAN`，副标题改为区域摘要，示例：

- `12 台 IPSAN，4 个资源组，9 台已归组，3 台未归组，设备缓存命中 5，资源组缓存命中 2`

右侧操作区：

- `刷新`
- 当前子视图对应的批量清理按钮

规则：

- `刷新` 总是同时刷新 `IPSAN/list` 与 `resourceGroup/list`
- 批量清理只作用于当前子视图
  - 在 `单台 IPSAN` 子视图中：清理单台 IPSAN 的缓存
  - 在 `资源组` 子视图中：清理资源组缓存

### 4.2 子视图切换

在 `IPSAN` 卡片内容区顶部新增胶囊切换：

- `单台 IPSAN`
- `资源组`

默认选中 `单台 IPSAN`。

切换子视图时：

- 不重新请求接口
- 直接复用当前内存中的两份结果
- 仅切换展示和批量动作目标

## 5. 单台 IPSAN 视图设计

### 5.1 表格列

单台 IPSAN 主表列调整为：

- `名称`
- `ID`
- `状态`
- `容量`
- `用途`
- `所属资源组`
- `缓存`
- `操作`

### 5.2 所属资源组展示规则

如果当前 IPSAN 属于某个资源组：

- 主胶囊显示：`RG: {groupName}`
- 次级小字显示：`{memberCount} 台成员`
- 提供轻量跳转入口：`查看资源组`

点击 `查看资源组` 后：

- 切换到 `资源组` 子视图
- 尝试高亮或定位到对应资源组行

如果当前 IPSAN 不属于任何资源组：

- 显示灰色胶囊：`未归组`

### 5.3 缓存列展示规则

当缓存不存在：

- 显示 `--`

当 Redis 不可用：

- 显示统一的 `Redis 不可用` 状态胶囊
- 不显示详情入口

当缓存存在：

- 同一行内显示 `缓存存在` 胶囊
- 在胶囊右侧直接放一个轻量详情入口

详情入口样式建议二选一，最终实现选其一并全局一致：

1. 眼睛图标按钮
2. 短文本按钮，如 `详情`

约束：

- 详情入口必须与“缓存存在”保持同一行
- 不允许再单独占一行
- 不允许继续使用当前笨重的矩形“查看详情”按钮块

### 5.4 行级操作

操作列继续保留当前单条清理按钮：

- `删除缓存`

仅当该行缓存存在且 Redis 可用时显示/可用。

## 6. 资源组视图设计

### 6.1 主表列

资源组视图为独立主表，列如下：

- `资源组名称`
- `Group ID`
- `状态`
- `容量`
- `用途`
- `成员数量`
- `缓存`
- `操作`

### 6.2 行展开

资源组行支持展开，展开后显示成员列表。

成员子表建议列：

- `成员名称 / IP`
- `IPSAN ID`
- `状态`
- `容量`
- `用途`
- `成员缓存`

成员子表只承担关系展示与辅助排查，不在成员子表里重复放主要清理按钮，避免和单台 IPSAN 主视图职责重叠。

### 6.3 资源组缓存列

资源组本身的缓存列规则与单台 IPSAN 保持一致：

- 无缓存：`--`
- Redis 不可用：不可用胶囊
- 有缓存：`缓存存在` + 同行轻量详情入口

### 6.4 资源组操作列

操作列保留资源组自己的单条清理按钮：

- `删除缓存`

该动作只删除资源组缓存，不联动删除其成员 IPSAN 缓存。

### 6.5 资源组与成员关系的视觉原则

资源组表负责表达“汇总”和“归属”：

- 组行是主信息
- 成员展开区是上下文
- 不把成员表设计成另一个完整操作工作台

这样可以避免资源组视图与单台 IPSAN 视图互相复制。

---

## 7. 缓存详情入口统一改造

### 7.1 要解决的问题

当前“缓存存在”与“查看详情”是上下堆叠关系，导致：

- 单元格高度不必要地变大
- 一整列显得拥挤且丑
- 用户把它误读成一个额外主操作

### 7.2 统一的新规则

所有缓存列统一改成以下形态：

- `缓存存在` 胶囊
- 紧邻其后的轻量详情入口

推荐视觉形态：

- 主元素：`缓存存在` 状态胶囊
- 次元素：无底色的图标按钮，或极轻的文本按钮
- hover 时强化边框/文字色，而不是做厚重按钮背景

### 7.3 应用范围

必须统一覆盖以下 4 个区域：

- Linux 本地盘表格
- Windows 分区表格
- 单台 IPSAN 表格
- 资源组表格

### 7.4 一致性要求

四个区域必须共用同一套组件或同一套模板规则：

- 相同图标
- 相同尺寸
- 相同 hover / focus 行为
- 相同 tooltip 文案

不得出现某些区域是眼睛图标，某些区域还是“查看详情”四个字按钮的混搭状态。

---

## 8. 状态与用途枚举统一

### 8.1 统一原则

`本地盘 / 单台 IPSAN / 资源组` 的状态展示统一复用现有状态体系：

- `statusLabelKey(code)`
- `statusBadgeClass(code)`
- `statusIsBusy(code)`

资源组 `groupStatus` 也必须走同一套颜色和标签映射。

### 8.2 状态说明区

当前页面已有状态说明区，本次应提升为整页共享含义：

- 不是“仅服务本地盘”
- 而是“本页所有资源状态码说明”

因此文案要改成跨区域表达，避免用户误解该 legend 只解释本地盘。

### 8.3 用途枚举

资源组、本地盘、IPSAN 的用途枚举统一使用同一套映射与样式：

- `usageLabelKey(code)`
- `usageBadgeClass(code)`

如果资源组接口没有返回用途字段，则在资源组视图中显示：

- `未设置`

但仍走同一套 badge 表达，不另发明新样式。

---

## 9. 空状态、错误态与加载态

### 9.1 单台 IPSAN子视图空状态

- 未查询前：沿用当前 `获取` 引导
- 查询后无 IPSAN：显示 `未返回 IPSAN 数据`

### 9.2 资源组子视图空状态

分两类：

1. 没有任何 IPSAN
   - 说明：`当前接入 IP 未返回任何 IPSAN，因此不存在资源组`
2. 有 IPSAN，但没有任何资源组
   - 说明：`当前存在单台 IPSAN，但未配置资源组`

### 9.3 加载态

资源组与单台 IPSAN 共用 `IPSAN` 区域请求过程，因此：

- 首次请求时，卡片级 skeleton / loading 可以共用
- 已有结果后二次刷新时，仅降低表格透明度并转动刷新图标

### 9.4 错误态

如果 `resourceGroup/list` 失败而 `IPSAN/list` 成功：

- `单台 IPSAN` 视图仍可展示
- `资源组` 子视图应显示错误提示
- `所属资源组` 列显示降级态，例如 `归属获取失败`

如果两个接口都失败，则维持当前 `IPSAN` 区域整体错误态。

## 10. 前后端改动边界

### 10.1 后端

建议补充新的资源组查询命令，至少新增：

- `disk_cleanup_list_ipsan_resource_groups`

返回资源组列表及成员结构。

是否把“归属关系推导”放在 Rust 层或前端层，均可接受；但无论放在哪一层，输出给页面的最终结果必须满足本设计中的关系字段需求。

### 10.2 前端类型

前端需要新增资源组相关类型，至少包括：

- `IpsanResourceGroupItem`

- `ipsanRowsWithGroupMeta`

## 11. 验证清单

### 11.1 关系展示

1. 有 IPSAN 且有资源组时：
   - 单台 IPSAN 视图可看到所属资源组
   - 资源组视图可看到成员列表
2. 有 IPSAN 但无资源组时：
   - 单台 IPSAN 视图中所有设备显示 `未归组`
   - 资源组视图显示“未配置资源组”空状态
3. 无 IPSAN 时：
   - 资源组视图提示“没有 IPSAN，因此没有资源组”

### 11.2 缓存详情入口

以下四处都必须确认已经从“堆叠按钮”改为“同行轻量入口”：

1. Linux 本地盘
2. Windows 分区
3. 单台 IPSAN
4. 资源组

检查点：

- 行高明显下降
- 缓存列不再出现双层按钮块
- 键盘 focus 样式仍然清晰
- tooltip / aria-label 完整

### 11.3 批量与单条动作

1. `单台 IPSAN` 子视图中的批量清理只清理设备缓存
2. `资源组` 子视图中的批量清理只清理资源组缓存
3. 资源组单条清理不影响成员 IPSAN 缓存
4. 单台 IPSAN 单条清理不影响所属资源组缓存

### 11.4 降级与异常

1. 仅资源组接口失败时，单台 IPSAN 仍可用
2. 资源组成员缺失时，页面显示异常提示而不是静默丢失
3. Redis 不可用时，详情入口不出现，清理按钮置灰

---

## 12. 不做项

本次设计明确不包含以下内容：

- 不把资源组提升为页面一级区域
- 不在资源组成员子表中重复放完整清理工作台
- 不做“清理资源组时顺带清理所有成员缓存”的联动语义
- 不引入新的状态颜色体系
- 不保留旧版“查看详情”大按钮样式
