# 视频设备模拟器实况时间水印功能规格

日期：2026-07-28  
状态：已批准实施  
适用范围：File Sync Tool 视频设备模拟器

## 1. 背景与目标

当前视频设备模拟器将素材包中的预编码 H.264 访问单元循环发送给 RTSP 客户端。实况画面本身不包含当前时间，因此 UMS、VLC、录像和回放均无法从视频内容确认模拟器发送画面的实际时间。

本功能在实况视频帧中烧录模拟器所在 Windows 电脑的当前本地时间，并提供持久化开关。水印必须成为编码画面的一部分，而不是仅在本工具前端叠加。

目标：

- 主、辅、第三码流均可显示当前时间。
- UMS、VLC、录像和回放看到相同的水印内容。
- 所有虚拟设备共享每种码流的处理管线，转码开销不随设备数或客户端数线性增加。
- 水印开关默认开启，用户可以关闭并恢复现有静态媒体发送路径。
- 无客户端拉流时不持续解码和编码视频帧。

## 2. 用户可见功能

### 2.1 时间格式

- 固定格式：`yyyy/MM/dd HH:mm:ss`。
- 示例：`2026/07/27 15:00:00`。
- 使用模拟器所在电脑的当前本地时间和本地时区。
- 每秒更新显示内容；视频仍按原始码流帧率输出。

### 2.2 显示样式

- 默认位置：画面右上角。
- 字体颜色：白色。
- 使用黑色描边或等效的深色背景保证明暗画面中的可读性。
- 字号、描边和边距按视频分辨率缩放。
- `640×360` 码流中不得裁切、溢出或遮挡大面积画面。
- 首版只包含 ASCII 数字、斜杠、冒号和空格，不依赖系统字体文件。

### 2.3 开关行为

- 在“设备配置 > 实况画面”区域增加“时间水印”开关。
- 开关默认开启。
- 设置随应用配置持久化。
- 模拟器运行期间开关随现有配置表单一起锁定。
- 修改开关后，下次启动模拟器时生效。
- 帮助文案需要说明：水印会进入所有实况和录像画面，并增加媒体处理开销。

### 2.4 可访问性

- 使用原生复选框或具备等效键盘语义的开关控件。
- 控件必须具备可见焦点状态、明确标签和至少 44×44 像素的点击区域。
- 禁用状态必须同时通过透明度和鼠标指针表达，不能只依赖颜色。
- 中英文文案同步维护。

## 3. 配置与兼容契约

### 3.1 持久配置

在 `DeviceSimulatorSettings` 中增加：

```text
last_time_watermark_enabled: boolean = true
```

要求：

- Rust 默认值为 `true`。
- TypeScript 默认值为 `true`。
- 旧配置文件缺少字段时迁移为 `true`。
- 保存配置时字段必须完整回写，不能被其它应用域配置覆盖。

### 3.2 启动请求

在 `StreamRuntimeConfig` 中增加：

```text
time_watermark_enabled: boolean = true
```

要求：

- 前端始终显式发送字段。
- Rust 反序列化缺失字段时使用 `true`，保持旧调用方和 Worker 协议兼容。
- 该字段进入主进程到提权 Worker 的初始化请求。
- 该字段不属于网络拓扑，但首版仍只允许在启动前修改。

## 4. 媒体处理架构

### 4.1 关闭水印

关闭水印时保持当前路径：

```text
SharedMediaPack -> SharedFrameScheduler -> RTP packetizer -> RTSP/TCP
```

不得启动解码器或编码器；输出帧、关键帧、SPS/PPS、码率和兼容行为保持现状。

### 4.2 开启水印

开启水印时使用会话级共享处理中心：

```text
SharedMediaPack
  -> Windows Media Foundation H.264 decoder
  -> NV12 frame
  -> time watermark renderer
  -> Windows Media Foundation H.264 encoder
  -> shared encoded access-unit broadcast
  -> per-client RTP packetizer
```

每个模拟器会话最多建立三条管线：主码流、辅码流、第三码流各一条。所有设备、NVR 通道兼容地址和 RTSP 客户端订阅相同码流类型的共享输出。

### 4.3 生产者所有权

- 共享转码生产者由 `ProtocolRuntime` 或其拥有的媒体中心统一管理。
- RTSP 端点和路由只能订阅媒体源，不能为同一共享媒体源重复启动生产者。
- 生产者生命周期早于 RTSP 监听器可用，停止顺序晚于所有 RTSP 客户端退出。
- 静态媒体调度与动态转码调度使用明确区分的媒体源抽象。

### 4.4 空闲与恢复

- 启动阶段允许短暂预热编码器，以获得实际 SPS、PPS、profile-level-id 和首个关键帧。
- 没有活动 RTSP 播放客户端时停止向解码器和编码器送帧，但可以保留已初始化的 MFT 会话。
- 首个客户端进入 `PLAY`/`FASTPLAY` 时恢复管线并请求关键帧。
- 最后一个客户端离开后允许短暂宽限期再暂停，避免快速重连导致频繁启停。
- 新客户端必须从关键帧开始接收，不能收到无法解码的增量帧。

### 4.5 视频时钟

- 水印文字使用系统本地时间。
- RTP 时间戳使用独立的单调媒体时钟。
- 系统时间前跳、后跳或时区变化不得导致 RTP 时间戳回退。
- 素材循环边界不得重置 RTP 时间戳。
- 编码器配置为低延迟、禁用 B 帧，并维持有界 GOP。

## 5. Windows 编解码策略

- 使用 Windows Media Foundation H.264 解码器和编码器。
- 优先选择硬件编码器；硬件不可用或运行失败时允许使用 Microsoft 软件编码器。
- 预检必须验证解码、NV12 输出、水印绘制、编码、SPS/PPS、IDR 和时间线，而不能只验证 MFT 是否可枚举。
- 三条管线需要同时预检，避免单个硬件会话可用但并发会话数不足。
- 可复用屏幕共享实现中的编码器候选选择、自检、低延迟参数协商、关键帧请求和 Annex-B NAL 解析逻辑，但 RTSP 管线不得依赖浏览器 fMP4 状态。
- 屏幕共享与视频设备模拟器同时运行时必须正确处理硬件编码会话竞争和软件降级。

## 6. SDP 与 RTSP 要求

- SDP 的 SPS/PPS 来自当前实际编码器输出。
- `profile-level-id` 从实际 SPS 推导，不使用固定常量。
- 编码参数发生代际变化时，旧 SDP 不得继续对外使用。
- 每个关键帧访问单元应包含或可配合发送客户端解码所需的参数集。
- 保持现有 RTSP/TCP interleaved、旧路径别名、无音频和客户端独立 SSRC/sequence/timestamp offset 行为。
- 慢客户端继续使用有界队列隔离，不能阻塞共享转码生产者。

## 7. 失败与降级策略

### 7.1 水印开启

- 优先硬件路径，失败后尝试软件路径。
- 三路任一路无法建立合法输出时，预检或启动失败。
- 错误信息必须说明失败阶段、码流和可操作建议，包括关闭时间水印后重试。
- 不允许静默发送无水印画面，因为这会违反用户明确开启的设置。

### 7.2 水印关闭

- 不检查编解码器能力。
- 编解码器不可用不得影响原有模拟器启动和 RTSP 实况。

## 8. 性能与资源目标

基准媒体目标：

- 主码流：`1920×1080@25fps`，目标码率约 `3.4 Mbps`。
- 辅码流：`640×360@20fps`，目标码率约 `0.5 Mbps`。
- 第三码流：`640×360@20fps`，目标码率约 `0.5 Mbps`。
- 三路合计像素处理量约等于一路 `1080p@30fps`。

验收目标：

- 批准硬件：8C/16T、32 GiB、1 GbE。
- 500 台虚拟设备在线、100 路 RTSP 并发。
- 硬件路径启用水印后，整机 CPU 增量不超过 10 个百分点。
- 服务端媒体处理新增延迟 P95 不超过 120 ms。
- 无活动拉流且预热完成后，不持续解码或编码帧。
- 无持续丢帧、RTP 时间戳回退、码流花屏或非预期断流。
- 网络码率以编码器实际输出和已发送字节为准，不使用静态素材码率代替。

软件编码路径不承诺与硬件路径相同的 CPU 门槛，但必须保持功能正确，并在日志或状态中明确标识软件降级。

## 9. 可观测性

至少记录或暴露：

- 水印是否启用。
- 每路管线的状态：预热、活动、空闲、失败。
- 编码器名称、硬件/软件类型和降级原因。
- 输入、解码、水印、编码和输出帧计数。
- 丢帧、编码失败和关键帧请求失败计数。
- 编码耗时和管线延迟。
- 实际输出码率。
- 活动 RTSP 客户端数和共享管线订阅数。

日志不得逐帧输出；重复错误应限频。

## 10. 测试规格

### 10.1 配置与契约测试

- 旧配置缺少水印字段时默认开启。
- 保存并重新加载 `false` 后保持关闭。
- TypeScript 与 Rust 字段名、默认值和序列化一致。
- 旧启动请求缺少字段时默认开启。
- Worker 初始化请求保留字段。

### 10.2 纯逻辑测试

- 时间格式固定为 `yyyy/MM/dd HH:mm:ss`。
- 跨分钟、跨天和闰日格式正确。
- 1080p 与 360p 水印边界、字号和右上角位置正确。
- 水印渲染只修改预期的 NV12 区域。
- RTP 时间戳不受系统时间回拨影响。
- 素材循环后媒体时间戳连续。
- 多个端点订阅同一码流时只存在一个生产者。
- 最后一个订阅者退出后管线进入空闲。

### 10.3 Windows 集成测试

- MF 解码得到合法 NV12 帧。
- 三路编码器同时建立并通过独立解码自检。
- 输出包含 SPS、PPS、IDR，且无 B 帧和非法时间线。
- 硬件失败时软件降级可用。
- 三路任一路完全不可用时启动失败。

### 10.4 播放与平台验收

- VLC 分别拉取主、辅、第三码流，水印清晰且每秒更新。
- UMS 实况显示水印。
- UMS 录像与回放包含水印。
- 中途断开重连后能在限定时间内从关键帧恢复。
- 水印关闭后 VLC 和 UMS 兼容行为与现有版本一致。

### 10.5 性能验收

- 10、100、500 台设备分别测试空闲、部分拉流和 100 路并发。
- 每档记录 CPU、GPU 视频引擎、RSS、实际码率、帧率、丢帧和断流。
- 同时开启屏幕共享，验证编码会话竞争和降级行为。
- 持续运行至少一小时。

## 11. 实施阶段

1. 增加规格、配置字段、默认值、迁移、前端开关和中英文文案。
2. 抽取可复用的 Windows H.264 MFT 基础层，建立单路解码、水印和编码原型。
3. 建立会话级三路共享媒体中心和动态 SDP。
4. 将 RTSP 端点改为订阅共享媒体源，实现空闲/恢复和关键帧门控。
5. 增加可观测性、配置测试、纯逻辑测试和 Windows 集成测试。
6. 完成 VLC、UMS 与 500 台/100 路性能验收。

## 12. 非目标

首版不包含：

- 自定义水印位置、颜色、字号或格式。
- 每台虚拟设备使用不同的水印内容。
- 摄像机名称、IP、通道名称等额外 OSD。
- H.265 水印转码。
- 运行中热切换水印开关。
- 依赖现场安装 FFmpeg。
- 仅在本工具预览页面叠加但不进入 RTSP 视频帧的伪水印方案。

## 13. 完成定义

只有同时满足以下条件才视为功能完成：

- 默认开启和持久化开关可用。
- 三路 RTSP、UMS 实况、录像和回放均能看到正确水印。
- 关闭水印时原有静态路径无回退。
- 共享管线不按设备或客户端重复编码。
- 失败和软件降级对用户可见。
- 针对性自动测试通过。
- 批准硬件上的 500 台/100 路性能门槛有实测记录。
