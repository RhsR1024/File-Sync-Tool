# 虚拟设备时间水印录像倍速问题复盘

日期：2026-08-10
状态：已定位并修复
适用范围：Windows 虚拟设备模拟器、开启时间水印后的 H.264 RTSP 实况与平台录像

## 1. 问题摘要

关闭时间水印时，平台实况、录像和回放速度正常。开启时间水印后，RTSP 实况仍然正常，但平台保存的录像在回放时出现约 25～30 倍的内容快进。

平台显示的录像时间范围仍然完整。例如录像段仍显示为 `16:00–16:02`，但实际播放 1 秒时，画面和烧录水印会向前跳过约 20～40 秒。烧录水印也同步快速前进，说明异常不是播放器顶部时间标签单独计算错误，而是录像中可解码的视频帧被快速消费。

## 2. 诊断证据

### 2.1 发送节奏正常

水印开启时的 `WM_DIAG` 与 `RTSP_DIAG` 显示：

- 编码输入、编码输出和发布帧率均约为 25fps。
- RTSP 接收和发送帧数相等，没有持续丢帧。
- 广播和客户端发送队列没有积压。
- RTP 媒体时间与墙钟时间比值约为 1.0。
- 仅观察到少数 66～142ms 的孤立调度停顿，不足以解释约 28 倍快进。

因此，问题不在水印渲染速度、发送节拍、RTP 持续加速或网络队列。

### 2.2 码流结构存在兼容差异

关闭水印时，RTSP 直接发送素材包中的 x264 H.264：

- High Profile、无 B 帧。
- 每两秒一个 IDR，其余为 P 帧。
- 每个访问单元包含 AUD，关键帧包含 SPS/PPS。

开启水印时，视频必须经过 Windows Media Foundation 解码、绘制和重新编码。MF 输出的 P Slice 符合 H.264 标准，FFmpeg/VLC 能完整解码，但其 Slice Header 表达、参考标记和 `frame_num` 等字段与素材中的 x264 输出不同。

目标平台能够正常显示这路实况，但录像解析器没有正确保留或索引 MF 产生的 P Slice。录像段的外层起止时间仍由平台正常保存，而视频内容主要剩下少量可识别帧；回放器再按正常视频帧节奏消费这些帧，最终表现为内容和烧录水印约 25～30 倍快进。

### 2.3 A/B 验证

将水印编码临时调整为每一帧都请求 IDR 后：

- 平台新录像回放立即恢复正常速度。
- 本机 MF→RTSP→FFmpeg 验证中，水印流 51/51 帧均为 IDR。
- 无水印对照流仍为 2 个 IDR 和 49 个 P 帧。
- 两路均保持 25fps 和 High Profile；本机编码器保持原始 Level，现场编码器可按码率预算安全提升 Level。

该结果确认根因是目标平台录像链对 MF 非 IDR/P Slice 的兼容问题，而不是播放器倍速设置或 RTP 发送速度。

## 3. 最终兼容方案

### 3.1 保持每帧独立可解码

水印编码路径采用以下约束：

- 每个输入帧都请求 IDR。
- GOP 间隔固定为 1。
- 禁用 B 帧。
- 保持输入素材的 H.264 Profile 和 CABAC 设置；Level 不得降低，但允许编码器按资源预算提升。
- 每个访问单元带 AUD；关键帧使用已发布的 SPS/PPS。
- RTP 时间戳量化到声明的固定帧率网格。
- 保留 RTCP Sender Report，供标准客户端建立墙钟与 RTP 时钟映射。

这些约束只作用于开启时间水印的转码路径；关闭水印时仍直接发送原始素材，不增加转码或码率开销。

### 3.2 补偿全 IDR 的画质损失

首次全 IDR 修复沿用了原素材为普通 GOP 设计的建议平均码率。由于每个 IDR 都必须独立描述整幅画面，无法复用相邻 P 帧，原码率不足时会产生明显块效应和模糊。

最终调整为：

- 离线素材主码流从 3.4Mbps 提升至 6Mbps，辅码流和第三码流从 0.5Mbps 提升至 1Mbps。
- 离线 x264 从 `veryfast` 调整为 `medium`，缩放明确使用 Lanczos，并保留 1.5 倍峰值和两秒缓冲。
- 水印编码目标平均码率仍以素材建议码率的 4 倍为基础；旧素材另设主码流 18Mbps、辅/第三码流 2.5Mbps 的最低全 IDR 预算，避免旧 manifest 继续限制画质。
- 目标码率硬上限为 100Mbps。
- 优先协商 Peak-Constrained VBR，其次 Low-Delay VBR，最后回退 CBR。
- 峰值码率预算为目标平均码率的 1.5 倍。
- 编码缓冲区设为目标平均码率的一秒数据量。
- 编码器启动摘要记录实际后端、硬件/软件路径、码控模式和平均/峰值预算，便于比较不同现场机器；该摘要每路只输出一次，不恢复高频诊断日志。

Level 不是画质档位，而是该码流所需解码资源上限。1080p25 全 IDR 提高平均和峰值预算后，部分 Media Foundation 编码器会把 High Profile 从 Level 4.0 自动提升到 4.1。该提升不改变 Profile、分辨率或帧率，且水印 SDP 的 `profile-level-id` 始终从编码器最终 SPS 派生，因此属于有效输出。启动校验只拒绝 Profile 改变或 Level 降级，不再把 4.0→4.1 误判为编码器不可用；编码器一旦发布 SPS，后续参数集变化仍会导致管线安全停止。

本机 1080p25 动态测试素材的约两秒输出结果：

- 全 IDR 水印流：51 帧、51 个 IDR、约 5.03MB。
- 原始 GOP 对照流：51 帧、2 个 IDR、约 0.96MB。

实际带宽和录像占用取决于画面复杂度与硬件 MFT 实现，但全 IDR 的资源消耗必然高于普通 GOP。这是当前兼容目标平台录像器所需的明确权衡。

离线素材新增 VMAF 质量门禁。构建或 CI 可直接对“源 MP4 + 任一路 media.json”抽取短样本，按 manifest 声明的 CFR 时间线比较画质；默认阈值为 80，可按具体素材建立更高基线。该门禁依赖构建机 FFmpeg/libvmaf，不进入桌面客户端，也不会改变运行时媒体时钟。

使用复杂车流素材前五秒做同源 A/B，参考画面按各路目标分辨率和帧率缩放后再比较：

- 主码流旧配置 VMAF `81.25`，新配置 `90.77`。
- 辅码流旧配置 VMAF `85.91`，新配置 `93.26`。
- 第三码流旧配置 VMAF `85.95`；其编码参数与辅码流一致，新配置短样本同为约 `93.26`。

该比较衡量的是“在各自目标分辨率内保留的细节”，不表示 640×360 辅流会达到 1920×1080 主流的绝对清晰度。辅流和第三流若要进一步提升绝对细节，必须提高分辨率，并重新评估多路带宽、编码负载和平台兼容性。

## 4. 排查期间改动的取舍

以下逻辑虽不是最终倍速根因，但属于正确的媒体协议和兼容性防护，继续保留：

- SPS VUI 帧率归一化及 `fixed_frame_rate_flag`。
- Profile、CABAC 一致性以及 Level 不降级校验；SDP 使用最终 SPS 的实际 Level。
- 固定帧率 RTP 时间戳量化和单调性检查。
- AUD、SPS/PPS 注入与去重。
- RTCP Sender Report。
- 有界广播及客户端写队列、等待关键帧门控。

以下现场诊断行为已收敛：

- 正常运行时不再每 5 秒输出 `WM_DIAG` 和 `RTSP_DIAG` 长日志。
- 仅在编码输出异常、非全 IDR、RTP 时间戳异常、客户端滞后或发送队列失败时输出诊断。
- 水印管线 active/idle 状态降为 debug 日志。
- 前端虚拟设备日志缓存从 2000 条降为 500 条，并统一执行裁剪。
- 移除测试期间用于保留原始 H.264 诊断文件的临时环境变量入口。

应用自己的 `app.log` 有 5MiB 和五代压缩轮转保护；Tauri 日志插件也有独立的小文件轮转。收敛周期日志后，正常长时间运行不会再持续刷入大量水印时序文本。

## 5. 回归测试要求

自动测试必须覆盖：

- 三路离线素材使用 6Mbps/1Mbps/1Mbps、`medium`、Lanczos，同时保持 25/20/20fps、两秒闭合 GOP、无 B 帧和 CFR。
- 水印编码目标码率按 4 倍放大，应用主/辅流最低全 IDR 预算，并受 100Mbps 上限约束。
- 峰值预算不低于平均码率，编码缓冲区和实际码控模式可从启动摘要核验。
- 水印流每个输出帧均为 IDR。
- 水印流与对照流帧率一致，且采集墙钟时长没有提前结束。
- 水印输出保持输入 Profile，Level 不得低于输入值，并允许 4.0→4.1 等安全提升。
- SDP `profile-level-id` 与编码器最终 SPS 保持一致。
- 全 IDR 输出具有相对普通 GOP 足够的实际码率余量。
- 健康的周期诊断窗口保持静默；异常窗口仍生成可导出的文本。
- 前端日志数组始终受固定条数上限约束。
- 素材构建质量门禁能重建 manifest NAL 并在 VMAF 低于阈值时失败。

现场验收必须使用新版本重新启动虚拟设备并生成全新录像；历史录像的封装和索引不会因程序升级自动修复。

## 6. 后续优化方向

当前方案优先保证目标平台兼容与画质，代价是更高带宽、录像空间和编码负载。若后续需要恢复普通 GOP 的效率，可选择：

1. 推动平台修复录像解析器，使其正确处理标准 MF P Slice。
2. 引入能够生成与素材 x264 结构一致的软件编码器，并完成许可、CPU 和部署评估。
3. 在明确验证平台支持后，按码流类型逐步放宽为短 GOP，而不能仅依据 VLC/FFmpeg 可播放就取消全 IDR。

在目标平台录像回放验证通过之前，不得恢复 MF P 帧，也不得只通过修改关键帧标志伪装非 IDR 帧。
