# 同步控制台长期运行问题排查

日期：2026-09-20。依据：当前仓库源码、用户截图和自动化回归测试。未访问故障电脑，未将开发电脑的进程或网络状态用于现场结论。

## 已确认并修复

- “立即扫描”的禁用条件原来是定时调度开启，而不是扫描正在执行。现在等待下次扫描期间可以手动触发，仅当前扫描尚未返回时禁用。
- 原先固定间隔触发扫描，扫描耗时超过间隔时仍会重复请求，遇到后端忙碌又启动另一套延迟重试。后端已有互斥，不能将其认定为复制任务无限并发；前端现在共用一个进行中的请求和一个后续定时器。
- 状态原来只显示调度开关。现在区分扫描处理中、等待下次扫描、等待复制队列和上次扫描有错误；显示实时扫描耗时或下次执行倒计时。新的间隔从本次扫描结束后开始计算。
- 停止调度会清理后续定时器，并使尚未完成的配置加载失效。停止不取消已经进行的复制；重新启动时复用尚未结束的扫描，不再启动第二次。
- 任务详情和分组日志原先不随任务删除释放。分组日志虽有单组上限，却没有所有组的总预算。现在清理已删除任务的缓存，详情最多缓存 32 组；所有任务日志合计最多 10,000 条、单组最多 2,000 条，达到上限时批量回收最旧的 10%，减少频繁复制和响应式数组移动。
- 通知追踪状态随任务移除释放；未能匹配任务快照的排队通知标记最多保留 1,000 个。
- 状态加载合并重复请求，实时快照到达后不再被较旧的查询返回覆盖；切换任务详情时也防止旧请求覆盖新选择。
- 可见主窗口每 30 秒补查任务列表，重新获得焦点或从隐藏恢复时立即补查，修复漏掉列表事件后的显示。后台隐藏时跳过补查。轮询和监听在主窗口卸载时清理。
- 日志达到显示上限后长度不变，原来的长度监听不再触发保存；改为监听最新一条日志。

## 尚不能归因于现场的风险

- 普通 `app.log` 已有 5 MiB 轮转阈值和最多 5 个压缩备份，没有发现无限追加同一日志文件的问题。
- 后端失败、取消、中断及曾经失败的任务历史不受成功记录上限约束；每组的运行与部署尝试也保留完整历史。这是现有保留策略，不是本次自动删除对象。长期频繁失败仍可能增加 `task_state.json`、内存和序列化成本。
- 日志落盘及 gzip 轮转仍是同步操作；部分共享文件元数据读取也使用同步接口。慢磁盘、网络共享故障时可能占住执行线程。本次没有改动这些底层路径。
- Windows 系统复制接口、网络共享、SSH 或外部脚本长期不返回时，前端显示耗时并不能让底层操作恢复。本次没有用前端超时强行释放后端执行器，避免旧复制还在运行时启动第二份任务。
- 本次没有证实操作系统句柄、原生线程或 WebView 自身泄漏，也没有覆盖所有可选工具的长期运行行为。

## 验证与现场复核

自动化覆盖长扫描期间模拟推进两周、等待期间手动扫描、复制队列延迟重试、停止及快速重启、配置加载竞态、扫描错误恢复、倒计时与按钮、状态返回乱序、超过一万组日志的缓存上限和清理。模拟时间测试不等于实际运行两周的压力测试。

验证命令：`pnpm check`、`pnpm lint`、`pnpm exec vitest run --config vitest.sync.config.ts`，以及 taskStateStore、syncTaskNotifications、SyncConsoleLayout、App.keepAlive、App.quitFlow、configStore 的 Node 测试和 `git diff --check`。未执行 Tauri release 打包、提交或发布。

现场再次出现卡顿时，保留当时的 `app.log` 及轮转日志，并记录文件同步工具进程及其 WebView 子进程的 CPU、专用内存、句柄数和线程数，比较刚启动和运行后的趋势。同时记录程序版本、启用的工具、复制模式、任务数量及最近一次扫描时间。`task_state.json` 的文件大小和记录数量有助于判断历史积累；日志和状态文件可能包含内部路径、服务器地址或业务信息，分享前按需要脱敏。
