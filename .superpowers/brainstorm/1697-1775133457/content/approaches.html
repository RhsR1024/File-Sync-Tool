Architecture Approaches

How to integrate local post-copy scripts into the existing system

A

Separate Types + New Module

LocalCommandGroup as an independent type alongside CommandGroup

New local_exec.rs module handles script execution

Pros

  • Clean separation: remote commands vs local scripts have different semantics (SSH vs subprocess)
  • LocalCommandGroup can carry on_failure field without affecting remote CommandGroup
  • Auto-interpreter detection logic isolated in its own module
  • Easier to extend independently (e.g., timeout, working directory per group)

Cons

  • Two similar-looking types in config — users may confuse them
  • Config file grows with a new top-level array
B

Unified CommandGroup + Discriminator

Single CommandGroup type with a target: "remote" | "local" field

Execution dispatched based on target type

Pros

  • One concept for users to learn — "command groups" that run either locally or remotely
  • Reuses existing UI components for command group management

Cons

  • Forced to add on_failure, interpreter logic to a type designed for SSH commands
  • Binding model becomes awkward: local groups don't need server_id
  • Existing remote-only code paths need guards everywhere
  • Breaking change to config format — migration needed
C

Separate Types + Inline in scanner.rs

Same as A but script execution logic lives directly in scanner.rs (no new module)

Pros

  • Fewer files — execution happens right where copy completes
  • All post-copy logic in one place

Cons

  • scanner.rs already 1500+ lines, adding script execution makes it harder to maintain
  • Mixes file-copy concerns with subprocess management
  • Harder to unit test interpreter detection and script execution independently

Recommendation: A

Separate types + new module. The remote and local execution semantics are fundamentally different (SSH session vs Windows subprocess). Forcing them into one type creates awkward conditionals everywhere. A dedicated local_exec.rs keeps scanner.rs focused and makes the script logic independently testable.
